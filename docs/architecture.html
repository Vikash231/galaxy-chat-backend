Agent Chat Blueprint

How the backend is split into services, how a chat turn flows from the browser through the API, the Trigger.dev workers, OpenRouter and Magica, and back. It also covers how authentication works at every boundary. Day 1 goal: one signed-in user sends a message, the agent streams a reply, runs Crop Image on the real Magica API, and the result survives a reload.

Repos galaxy-chat-backend (monorepo) · galaxy-chat-frontend Deploy api → Vercel · worker → Trigger.dev cloud Source of truth Postgres Realtime Trigger.dev streams + run metadata

1Services and responsibilities

The backend is one pnpm-workspace repo. Each deployable service is a folder under apps/ with its own Dockerfile. Shared logic lives in packages/ and is never deployed on its own. Services talk to each other only through Postgres and Trigger.dev, never by importing each other.

2.2 Authentication and authorization

There are four credentials, one per boundary. Each is checked where it enters.

BoundaryCredentialIssued byVerified byLifetimeScope
Browser → apiClerk session JWT (Authorization: Bearer)Clerk (via getToken())api middleware: RS256 signature with CLERK_JWT_KEY, exp/nbf, azp ∈ FRONTEND_ORIGIN~60 s, auto-refreshed by the SDKOne user (sub)
Browser → Trigger.dev realtimePublic access token (JWT)api, after an ownership checkTrigger.dev1 h, refreshed via POST /runs/:id/tokenRead-only, one run
api / worker → Trigger.devTRIGGER_SECRET_KEYTrigger.devTrigger.devStatic secretProject
worker → OpenRouter / MagicaAPI keysProvidersProvidersStatic secretAccount
Magica → Trigger.devToken callback URL (unguessable)Trigger.dev wait.createTokenTrigger.dev10 minCan only wake one run; the payload is ignored and the result is re-fetched with GET

Authorization is enforced in the data layer. Every repository read or write takes userId and puts it in the WHERE clause (chats.getOwned(userId, chatId)). Route handlers can't import Prisma; a lint rule enforces this. A resource that doesn't exist and one owned by someone else both return 404 not_found, so nothing leaks. Workers never receive user input as authority: the payload is only IDs, and all state is reloaded from the DB.

3API reference (Day 1)

All request and response bodies are Zod schemas in @gx/contracts and appear in /api/openapi.json. The frontend's types are generated from that file, so there are no hand-copied types.

4Lifecycles of the major APIs

Step by step, with the component responsible for each step, what gets written, and what happens when that step fails. Timings marked "est." are estimates; nothing here has been measured yet.

4.1 Every authenticated request (the withRoute pipeline)

  1. middlewareRead or create X-Request-Id, then bind the logger context {traceId, method, path}. OPTIONS gets the CORS answer and returns here.
  2. middlewareCORS: Origin must equal FRONTEND_ORIGIN.Mismatch → no CORS headers, so the browser blocks the response.
  3. @gx/authExtract the Bearer token and verify the RS256 signature with CLERK_JWT_KEY (no network, <1 ms est.). Check exp, nbf and azp.Any failure → 401 unauthenticated. The client refreshes its token once and retries.
  4. @gx/authUpsert the user by clerkId (lazy provisioning). On insert, write the grant:<userId> ledger row and balanceMicro in the same transaction. The unique keys make parallel first requests safe.
  5. rate-limitSend route only on Day 1: count this user's AgentRun rows in the last 60 s (index (userId, createdAt)). Other routes get a RateLimiter backend on Day 2, behind the same interface.Over the limit → 429 + Retry-After.
  6. zodParse params, query and body with the route's contract.422 validation_failed with issue paths.
  7. handlerCall the service or repository with principal.userId. Ownership is part of the query itself.Not owned or missing → 404 not_found.
  8. with-routeSerialize through the response schema (which also removes internal fields) and set X-Trace-Id. Any thrown AppError becomes the error envelope; anything else becomes 500 and is logged with its stack.

4.2 POST /v1/chats/:chatId/messages: send a turn

  1. webGenerate a clientMessageId (uuid) and add an optimistic user bubble. Disable send while the request is in flight.
  2. apiRun the request pipeline (4.1): auth, rate limit (10/min), Zod text ≤ 8000.
  3. apichats.getOwned(userId, chatId).404.
  4. apiAdmission: balanceMicro ≥ MIN_ADMISSION_MICRO (5,000 = the cheapest tool call).402 insufficient_credits. Nothing is saved.
  5. api · txBEGIN → insert Message(user, clientMessageId) → insert AgentRun(queued) → update Chat.updatedAt → COMMIT.P2002 on clientMessageId → load the existing run and return 200 with the same body (safe replay). P2002 on the partial active-run index → 409 run_active + activeRunId.
  6. apitasks.trigger("agent-turn", {runId}, {idempotencyKey: runId, concurrencyKey: chatId}), then save triggerRunId.Trigger.dev error or timeout (5 s) → mark the run failed(dispatch_failed), which frees the active-run slot, and return 503. The user message stays and the UI offers "Retry".
  7. apiReturn 202 with {chatId, messageId, runId, realtime}. The public token comes from the trigger handle (read access to this run, 1 h).
  8. webInvalidate the messages query (the user bubble is now real). Start useRealtimeRun + useRealtimeStream("assistant") and show the status "thinking".

4.3 agent-turn task lifecycle (worker)

  1. startLoad AgentRun + chat. If it's already terminal, return, which makes redelivery idempotent.
  2. startSet AgentRun.status=running. Upsert the assistant Message(runId, status=streaming, content=[]); the unique runId makes this safe on retry. Set meta.status="thinking".
  3. contextLoad the last 40 messages, parse each with ContentBlock[], and map them to OpenAI-format messages: tool_use → tool_calls, tool_result → role:"tool". Build tool specs from the registry (z.toJSONSchema(tool.input)).
  4. step nStream OpenRouter. Text and reasoning deltas → coalescer → assistantStream.append({t, step, d}). Tool-call fragments are assembled by index.429/503 → backoff 1 s, 3 s, 9 s → llm_unavailable ("Free models are busy, retry in a minute"). Empty stream → one retry → llm_empty_response.
  5. checkpointAppend this step's blocks to Message.content, set checkpointStep=n, and add to AgentRun.routedModels, steps and usage. This is one write per step.
  6. toolsFor each call (in parallel): registry lookup → JSON.parse → tool.input.safeParse.Unknown tool, bad JSON or invalid args → tool_result error sent back to the model, which lets it correct itself on the next step.
  7. toolsCredit gate: balanceMicro ≥ tool.estimateMicro(input).Not enough → mark the tool failed(insufficient_credits) and stop the loop. Completed work stays; the turn finalizes as failed with a clear message.
  8. toolsUpsert ToolInvocation(runId, toolCallId, seq, input=sanitized). Update meta: tool running, label "Cropping image…". Then magicaRun.triggerAndWait({toolInvocationId}, {idempotencyKey: toolInvocationId}).
  9. settleOn a completed tool, in one transaction: ledger tool:<id> -creditsMicro + UPDATE User SET balanceMicro = balanceMicro - x. P2002 means it's already settled, so skip. Append the tool_result + asset blocks; meta sets the tool to completed with assetUrl.
  10. loopAppend results in seq order (the order is deterministic even though the calls ran in parallel), then go to the next step, up to AGENT_MAX_STEPS (8).
  11. finalizeNo tool calls → Message.status=success, AgentRun.status=completed, finishedAt, meta.status="complete". Log run.finished with the duration, steps and credits.
  12. failureAny terminal error → Message.status=failed + SafeError; the saved partial text, tools and assets stay. AgentRun.status=failed, meta.status="failed". The error is re-thrown as retryable only if no side effect is at risk; otherwise AbortTaskRunError.
  13. cancelonCancel: flush the coalescer, then save partial text as cancelled and set meta.status="cancelled".

4.4 magica-run task lifecycle (worker, queue tool-runs)

  1. loadLoad the ToolInvocation. If it's terminal, return the stored result (no Magica call).
  2. tokenwait.createToken({timeout:"10m", idempotencyKey:"magica:"+id}). A retry gets the same token back (isCached).
  3. guardLive mode only: reserve the estimate in one statement, UPDATE "ProviderSpendDaily" SET "spentMicro" = "spentMicro" + est WHERE provider='magica' AND day=CURRENT_DATE AND "spentMicro" + est <= cap. It reads and locks one row. Settlement later adds actual − estimate in the ledger transaction.0 rows updated → failed(spend_cap), with the user message "Tool budget reached for today". Concurrent calls can't overshoot the cap.
  4. dispatchSet status=dispatching, then POST /v1/nodes/crop_image/run with the mapped input and webhook:{url: token.url, events:[completed, failed, canceled]}, then save magicaRunId and status=running.400 → failed(invalid_input, Magica message). 401 → failed(unauthorized) + an error log. 403 → failed(provider_credits). 404/410 → failed(model_unavailable). 429/5xx/timeout → task retry (3×, backoff 2 s ×2).
  5. crash windowOn retry with status=dispatching and no magicaRunId, we can't tell whether Magica accepted the POST. We never POST again; we fail with dispatch_uncertain, which is retryable by the user. This trades a rare failed tool for never double-charging.
  6. waitwait.forToken(token.id). The run is checkpointed and uses no compute. Magica's webhook POSTs to the token URL.
  7. reconcileGET /v1/nodes/runs/{magicaRunId} (source of truth). If it isn't terminal, wait.for(5s) and GET again, up to 60 times (5 min). This covers a lost or early webhook and a token timeout.Still not terminal → failed(provider_timeout). The Magica run ID is kept for later reconciliation.
  8. persistCOMPLETED → tool.magica.fromMagicaOutput(output) (Zod) → output, creditsMicro=creditUsed, durationMs, completed. FAILED/CANCELED → the matching status + userMessage. Return the typed result to agent-turn.

4.5 Reload recovery and token refresh (GET /chats/:id, GET /messages, POST /runs/:id/token)

  1. webGET /v1/chats/:chatId → activeRun. If it's null, render history only and stop here.
  2. webGET /v1/chats/:chatId/messages → the assistant message has status=streaming and a checkpointStep.
  3. apiPOST /v1/runs/:runId/token: ownership check via AgentRun.userId, then mint a read token for triggerRunId.
  4. webSubscribe to metadata + the assistant stream from index 0. Render saved blocks for steps ≤ checkpointStep, and live parts only for later steps. That's what prevents duplicated text.
  5. webOn a transport error, retry with backoff 1, 2, 4, 8, 16 s. After 5 failures, switch to polling GET /v1/runs/:runId every 3 s and keep trying realtime in the background.
  6. webWhen meta.status is terminal, invalidate messages. The saved row replaces the live bubble, and there's exactly one terminal message.

4.6 POST /v1/runs/:runId/cancel

  1. apiRun the pipeline (4.1), then load the run via AgentRun.userId. If it's already terminal → 200 with the final status.
  2. apiruns.cancel(triggerRunId) → 202 stopping. The UI shows "Stopping…" straight away (optimistic).
  3. workeronCancel in agent-turn: flush the stream, save partial content, Message=cancelled, AgentRun=cancelled. Child magica-run tasks are cancelled too.
  4. workerA Magica run already in flight may still finish on Magica's side. A cancelled invocation keeps its magicaRunId, and a later GET-based reconcile records the real charge so the ledger matches the provider.
